| Mutation-notify still reads the search index, with no witnessed failure | `mutation-notify.sh:99` used `gh issue list --search 'in:title "..."'`, which is served from GitHub's eventually-consistent search index while `--label` is not. The 2026-09-01 spec removes `--search` from THIS site as a side effect of adopting per-workflow labels, so this row is about the pattern, not that line. **Read the refutation before acting:** the originating claim was that #99 duplicated an open #98. It did not — `gh api repos/brujack/math/issues/98/timeline` shows the bot closed #98 at 02:03:40 and the operator reopened it at 02:14:31, 54 seconds AFTER #99 was created at 02:13:37. Across all four issues: six correct notify decisions, zero duplicates, zero misses, and the query has returned `98` on every hand-run including 2026-09-01. So there is no measured defect here — only a mechanism that could fail and never has. Anyone reviving this should first look for a witnessed empty result, not re-derive it from issue counts or `state` fields. |
| Neither mutation workflow has a `concurrency` block, and the obvious scope is the wrong one | `grep -n concurrency .github/workflows/mutation-testing*.yml` returns nothing. **The race is refuted** — all 12 runs in the workflow's history are strictly sequential, gaps 21s–5m27s, the 2026-08-01/02 cluster being an operator hand-testing ADR-0024. So this is prophylaxis with no incident behind it. Two things a future author needs. **Scope it to the `notify` job, not the workflow:** serialisation only protects the issue lookup, which lives entirely in `notify` (one checkout + one download + one script, seconds), while workflow scope serialises `mutants` at `timeout-minutes: 360` — a six-hour queue to protect a ten-second one, and pending-run eviction becomes unreachable under job scope because it would need three multi-hour runs finishing seconds apart. **And `cancel-in-progress: false` still permits pending eviction:** GitHub keeps at most one pending run per group, so a third arrival silently cancels the queued one — invisible to the notify job, which attributes runs that die, not runs that never start. Cancelling in-progress instead is worse: it manufactures the terminated-job case notify reports on. |

## Adding a new entry

When a new spec or plan is created, add a row to the All Plans table. Set status to **In Progress** when implementation starts, **Done** when the PR merges. Also add a `> **Status: DONE**` banner at the top of the plan file once complete. Move backlog items to the All Plans table when their spec is written (remove the strikethrough pattern — just delete the backlog row).
